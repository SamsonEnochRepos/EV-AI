# Decisions

Each entry: what was decided, why, and what evidence backs it. Entries marked **(pending)** get
their numbers filled in once the benchmark has actually been run on this machine.

## D1. Python 3.12 via uv, not the system Python 3.14
The machine has only Python 3.14. `ctranslate2` (faster-whisper), `onnxruntime`, `piper-tts` and
`PySide6` ship wheels for 3.11/3.12 first; 3.14 wheels are not reliably available. `uv` was
installed with `pip install --user uv` and provisioned CPython 3.12.16 into `.venv`.

## D2. Real OS is Windows 10 Home (build 19045), not Windows 11
The brief says Windows 11. `Get-CimInstance Win32_OperatingSystem` reports Windows 10 Home.
Impact: none of the chosen components need Win11. The overlay uses Win32 extended window styles
that exist on both. Win11-only effects (Mica, rounded-corner DWM attributes) are not used.

## D3. Hotkey defaults
`Ctrl+Shift+Esc` opens Task Manager, so it is not used. Defaults (all in `config/ev.toml`):
push-to-talk `Ctrl+Alt+Space`, kill switch `Ctrl+Alt+Shift+K`, confirm yes `Ctrl+Alt+Y`,
confirm no `Ctrl+Alt+N`.

## D4. Ollama model candidates
Already installed: `llama3.2` (3B), `qwen2.5:3b`, `qwen2.5:7b`. Pulled for the benchmark:
`qwen3:4b` (thinking disabled via `think=false`), `moondream` (VLM). `qwen2.5:7b` is excluded
up front: 4.7 GB cannot fit in 4 GB VRAM.

Speed/VRAM benchmark (`python -m ev.evals.bench llm`, num_ctx 2048, 3 prompts, raw data in
`evals/results/bench_llm.json`):

| Model | tok/s (median) | Model size | In VRAM | Spill to RAM |
|---|---|---|---|---|
| qwen2.5:3b | 79.6 | 2.09 GB | 2.09 GB | 0% |
| llama3.2 (3B) | 76.9 | 2.32 GB | 2.32 GB | 0% |
| qwen3:4b | 28.5 | 3.23 GB | 2.34 GB | **27.6%** |

`qwen3:4b` fails the "no spill into system RAM" requirement at 2048 context and is about 3x slower,
so it is rejected for the voice path. The peak-VRAM column in the raw JSON is not reliable for the
second and third models because the previous model had not yet unloaded when the baseline was taken.
Both remaining candidates meet the 20 tok/s budget by a wide margin. The tool-accuracy and persona
comparison between qwen2.5:3b and llama3.2 is still **pending** (needs the venv install to finish).
Working default: `qwen2.5:3b`, fallback `llama3.2`.

## D5. Overlay toolkit
Candidates: PySide6 (Qt) vs Tkinter canvas. Tk cannot do per-pixel alpha or anti-aliased edges on
a transparent window without a colour-key hack (jagged edges). Qt does both natively. Final
choice: **PySide6 (Qt)**. Measured by `python -m ev.evals.bench overlay` (12 s of the `--demo` cycle,
whole process tree, raw data in `evals/results/bench_overlay.json`):

| Toolkit | CPU (mean, % of all cores) | CPU max | RSS | Edges |
|---|---|---|---|---|
| Qt | 0.01% | 0.26% | 52 MB | anti-aliased, per-pixel alpha |
| Tk canvas | 0.14% | 0.52% | 34 MB | aliased (colour-key transparency) |

Both meet the animating-CPU (< 1-2%) budget. Qt is 52 MB, inside the 60 MB budget but with less headroom.
Tk is lighter on RAM but cannot render smooth translucent rounded ends, so it is demo/benchmark-only.
Caveat: the 12 s sample covers part of the demo cycle including its hidden phase, so mean CPU is a blend.
Note: on this machine `.venv\Scripts\python.exe` is a launcher shim that spawns the real interpreter, so the
overlay is a process *tree*; the client kills the whole tree and benchmarks sum over it.

## D6. Overlay IPC
Overlay process is the TCP server bound to `127.0.0.1` on an ephemeral port. A random per-session
token is passed to it over stdin (not argv, which other processes can read) and must be the first
line a client sends (constant-time compare, 2 s deadline). Non-loopback peers are dropped. When the
authenticated core connection closes, the overlay exits; if the overlay dies, the core swallows the
error and restarts it with a cooldown.

## D7. Control tools are `safe` at tool level, with argument-level escalation
Per-click confirmation would make screen control unusable. Instead the policy engine escalates
based on arguments: clicking a control named like send/submit/delete/buy/pay/install... and
pressing Enter/Delete/Ctrl+W need spoken confirmation; password-like targets and sensitive windows
are blocked, and the control layer re-checks the *resolved* UIA element (including the
`IsPassword` property) before acting. Residual risk: Enter inside a web form is confirmed
conservatively, which costs one extra "yes" in normal typing flows. Edit `confirm_key_combos`
in `policy.toml` to relax.

## D8. Wake word
openWakeWord has no pretrained "Hey EV". Wake word is an optional, pluggable listener
(`trigger.mode = "wakeword"`, `wakeword_model`); it started with the placeholder `hey_jarvis`. A custom `hey_evie`
model was then trained with `scripts/wakeword/` and is now the configured default; the push-to-talk hotkey still
works in every mode. See `docs/PROJECT_DOCUMENTATION.md` for the training results and what was not measured. Models live in `models/openwakeword/` and are
fetched once by `scripts/download_models.py --wakeword`; nothing is downloaded at runtime. The push-to-talk
hotkey keeps working in wake-word mode.

## D9. Vector memory
SQLite facts + rolling summary only. ChromaDB would cost hundreds of MB of RAM on an 8 GB machine.

## D10. STT model: `base` (int8, CPU)
`python -m ev.evals.stt_eval`: 30 Piper-synthesized utterances (commands, numbers, app names, chat), clean and
with white noise at 10 dB SNR (raw data `evals/results/stt.json`).

| Model | WER clean | WER 10 dB | RTF median | RTF p95 |
|---|---|---|---|---|
| base | 8.6% | 8.6% | 0.23 | 0.33 |
| small | 9.0% | 8.2% | 0.65 | 0.93 |

`small` misses the RTF < 0.5 budget on this CPU and is not more accurate here, so `base` is the default
(`stt.model` in `ev.toml`). **Caveat:** the test audio is synthetic speech from one voice, so absolute WER is
optimistic versus real human speech, accents and room noise. No real-speaker recordings were available to me.

## D11. Vision fallback model: `qwen2.5vl:3b` (replaces moondream as default)
`python -m ev.evals.vlm_bench`, 5 UI-reading tasks on rendered images (read an order number, a meeting day, list
buttons, battery level, Bluetooth state), raw data `evals/results/bench_vlm.json`:

| Model | Accuracy | Warm latency | First load |
|---|---|---|---|
| moondream | 2/5 (40%) | 0.4 s | 4.1 s |
| qwen2.5vl:3b | 5/5 (100%) | 1.5 s | 5.9 s |

Moondream often returned an empty string or misread text. Qwen2.5-VL 3B is 3.2 GB, so it is **only usable because the
chat model is unloaded first** (`VLM.describe` does that, then unloads itself with `keep_alive=0`). The spill figure
measured while the chat model was still resident is not representative; the clean figure is in `EVAL_REPORT.md`.
MiniCPM-V and larger models were not tried: they do not fit in 4 GB VRAM next to a KV cache.
The VLM is a last resort. For reading text, UIA (0.03 s) and OCR (about 4 s cold) are used first.

## D12. Runtime is offline for models
A network audit of the real process showed a connection to a CDN at idle: faster-whisper checks the Hugging Face Hub on
every model load. EV now loads Whisper with `local_files_only=True`, sets `HF_HUB_OFFLINE=1` and the telemetry opt-outs
in `ev/__main__.py`, and fails with an actionable message if the model is missing (`scripts/download_models.py`).
`web_search` pins ddgs to the `duckduckgo` backend (default `auto` queried several search engines).
After the fix the idle process tree talks only to `127.0.0.1`.

## D13. VAD: Silero (streaming) with energy fallback
`faster_whisper.vad.SileroVADModel` is a stateless batch wrapper; EV drives its ONNX session directly with persistent
LSTM state, 512-sample chunks and a 64-sample context. On Piper speech vs noise/silence: Silero detected 94% of speech
blocks (energy VAD 83%) with 0% false positives on noise and silence, at about 4 ms per audio-second.
If Silero cannot load, EV falls back to the energy VAD.

## D14. Spoken-text sanitiser
A 3B model ignores "no lists / no percent signs / no URLs" often enough to matter. `ev/llm/spoken.py` enforces the voice
rules on every sentence before TTS (markdown, list markers, emoji, `%`, `$`, URLs become spoken forms such as "google dot com").
Persona pass rates in the report are for what EV would actually say, not raw model output.

## D15. Models and tools that were rejected
* `qwen2.5:7b`: 4.7 GB, cannot fit. `qwen3:4b`: 27.6% of the weights spill to RAM at 2048 context and it is about 3x slower.
* `llama3.2` 3B: fits and is fast, but scored 68% on tool choice and called `type_text` for plain chat.
* Tk overlay: kept only for the toolkit benchmark.

## D16. Git
`git init` was run and `.gitignore` written, but **nothing has been committed**: the housekeeping hook configured for this
workspace says not to commit.

## D17. Real-use fixes: STT model, Kokoro voice, reply length
Live testing showed mishearing, a robotic voice and long replies. Changes, with what was and was not measured:
* **STT**: `distil-small.en`, beam 3. On this CPU (20 synthetic utterances, `evals/stt_eval.py` clips) RTF was base 0.25,
  small 0.8, distil-small.en 0.65. WER was about 11% for all of them, so **this benchmark cannot show the accuracy gain**
  (same caveat as D10: synthetic single-voice speech). The choice rests on `small`-class models being known to handle accents
  and noise better than `base`, not on a measurement here. Whisper encodes a fixed 30 s window, so cost is roughly
  per-utterance, not per-second. Roll back with `stt.model = "base"`.
* **TTS**: Kokoro was already installed. Steady-state RTF about 0.44 vs Piper 0.09, so the first sentence starts about 1 s
  later; it is warmed up at load and `app.py` falls back to Piper if it fails.
* **Length**: the 3B model ignored "one to three sentences", so `Brain` now stops generation at `llm.reply_max_sentences`.
  Persona eval after the rewrite: 30/30 deterministic, judge mean 4.69/5.

## D18. Closing apps, websites, screenshots, administrator rights
* **Ask only for what is risky.** `close_app` (polite), `open_website` and `take_screenshot` are `safe`. Force-closing, anything mentioning administrator rights, and any address that isn't a known or trusted site (an automated review showed that gating only `?`/`#` missed data in hostnames and paths) escalates to confirm in `policy.py`; protected processes are blocked. All of it is decided from config and arguments, never from model or screen text.
* **Why `open_website` and not clicking.** "Open YouTube and search X" through the screen agent is 4-6 model steps of clicking; building the search URL is one deterministic call. `build_url` is a pure function the policy also calls, so the policy judges the exact URL that would open. Its first version crashed the policy on `javascript:alert(1)` (found by a test); it now rejects non-web schemes and never raises.
* **Polite close.** `WM_CLOSE` to every window of the app (same as the X button). Browser tabs never match by title, so "close YouTube" can't shut the whole browser. EV's own process, its terminal and its Python helpers are skipped; apps EV launched are not, which a live test showed (EV started Notepad as a child process and then refused to close it).
* **Not built:** a `delete_file` tool. The policy still lists `delete_file`, `move_file` and `send_message` as `confirm`, but nothing registers them, so EV cannot delete or send anything yet.
* **Measured:** 307+ unit tests, security suite 96/96 with 0 bypasses, intent eval 62/72 (4 of 6 new phrasings route to the right tool on `qwen2.5:3b`; "get rid of the Notepad window" and "pull up the Rust subreddit on Reddit" got a text reply instead of a tool call). Persona eval is 29-30/30 and varies run to run on a 3B model.

## D19. Display mode (text card on the pill)
* **One window, not two.** The card is drawn by the existing pill widget (the window just gets taller), so it shares the pill's fade, always-on-top, click-through and no-focus behaviour. The pill stays where it is; the toolkit-independent model is `overlay/display.py`.
* **Only while on.** The core sends transcript text to the overlay only in display mode, and the overlay keeps just the latest exchange in memory. Nothing is written to disk.
* **What it shows.** The user's line appears after transcription (Whisper runs on the finished utterance, so there are no live partial words), and EV's reply is added sentence by sentence as each is queued for speech; an interrupted reply shows only what was spoken. Confirmation prompts and agent narration appear too.
* **Tried and removed: hiding the card from screen capture.** The idea was to keep EV's OCR and screenshots from reading its own transcript. `SetWindowDisplayAffinity` fails on the pill (error 8, even in monitor mode; probably because it is a layered, translucent window, not confirmed) and the card showed up in captures. It was removed rather than shipped as a no-op. Consequence: in display mode, `screenshot_describe` and OCR-based `read_screen` can see the card. UI Automation reads, the default, only see the foreground window.

## D20. Voice barge-in on speakers: model the echo, don't compare levels
Recording EV speaking through laptop speakers while the mic listened (nobody talking): mic rms 0.02-0.05 while EV talks (a person at the mic is about 0.05-0.1), arriving about 480 ms after the playback meter, envelope correlation 0.88 once aligned. The first detector compared mic level to playback level at the same instant and calibrated in the first 600 ms, before the echo arrived (ratio 0.009), so it fired on 2 of 3 recordings. The replacement estimates the delay by cross-correlation, predicts echo as gain x playback delayed by that amount (gain = 75th percentile of recent samples, frozen while a possible interruption is in progress), and arms only after 1.2 s of playback. Margin 1.5 was chosen from a grid over margin and gain percentile: the longest false "suspect" run on real echo was 5 of the 10 blocks needed to fire, and simulated talk-over at 0.08 rms or louder was detected in every trial (median 0.4-0.7 s). **Limits:** the user's voice is simulated by adding a modulated tone to real echo levels, not recorded; a quiet voice (0.06) is caught in about 4 of 6 trials; without echo cancellation, a quiet talker over loud speakers cannot be told from EV's own voice. Headphones remove the problem. If EV still cuts itself off, raise `interrupt_margin` or set `voice_interrupt = false`.

## D21. Response time and conversation feel: what was measured decides what is on
Goal: faster replies and a less walkie-talkie feel, without touching the safety path. Measured on this machine with the real Ollama (`qwen2.5:3b`), one run each unless a count is given:
* **Warm up with the real prompt (on).** The old warm-up sent a bare "hi", so the first real turn still processed the persona and ~20 tool schemas (~2.9k tokens). `Brain.warm()` now sends the real system prompt and tool list, so Ollama's prompt cache holds them. First speech after a cold model: **0.23 s** after the real-prompt warm-up vs **1.04 s** after the old bare warm-up (second turn 0.26 s). The cache only helps while the prefix is byte-identical, so the system prompt no longer carries the minute-level clock (it was invalidating the cache every minute): it has the date and part of the day, and the exact time is the `get_time_date` tool's job (the fast path already answers "what time is it"). The cache is also lost when the screen tools swap the chat model out, or after the summary call, so the client tracks that (`OllamaClient.is_cold`) and `Brain.rewarm_if_cold()` reloads the model in the background while the user is still speaking; the summary thread re-warms after itself.
* **Summary off the critical path (on).** The rolling-summary model call (every 8th turn) ran inline and delayed the end of that turn; it now runs on a background thread.
* **One fast-path match per turn, one tool-schema token count per registry change (on).** Small, but it ran on every turn.
* **Start-up warm-ups in parallel (on).** Speech model (plus a throwaway decode), voice model (a discarded synthesis, serialised with real speech by a lock), LLM prompt, and the app list. The Start-menu walk (50-300 ms, done up to four times per launch) is cached for 5 minutes and rebuilt once on a miss; the Store-app list (a PowerShell call, 1-2 s) is built ahead of time. Weather reuses one HTTP connection and caches geocoding (24 h) and forecasts (5 min). **Not measured:** the gain of these four; they remove work, but no before/after timing was taken.
* **Whisper `without_timestamps` (on).** Utterances are at most 15 s (one window), so timestamps aren't needed. **Not measured.**
* **Parallel tool batches (on, narrow).** When one model turn asks for several tools and all are side-effect free (`get_weather`, `web_search`, `get_time_date`, memory, timers, reminders), they run at the same time (test: two calls that only finish if concurrent). UI tools keep their order. Gating still happens one call at a time, on the calling thread, because confirmations are spoken. The tool pool grew from 2 to 6 workers so a batch plus the screen agent's nested calls cannot starve.
* **"One sec" filler (on).** If a slow tool (search, weather, screen read) is still running after `llm.filler_after_s = 1.3`, the system says a short varied phrase. It is system text, not model output, and is not stored in history. **Not measured live:** the timing is covered by tests only.
* **Smalltalk without the model (on).** A bare "thanks", greeting or goodbye gets a varied canned reply instantly. "yes", "okay" and "later" are deliberately excluded: they can answer a question EV just asked and need the history.
* **Follow-up window grows with the conversation (on).** +2 s per back-to-back turn up to 15 s (`conversation.followup_patience_s`, `followup_window_max_s`), and hesitation sounds ("hmm", "um") in a follow-up are dropped like other noise.
* **Direct tool replies (built, off).** Speaking a finished tool result ("Opened Spotify.") instead of a second model call looked like the biggest saving. Measured over 6 action turns each: **median 0.30 s direct vs 0.28 s rephrased**, i.e. nothing, because the warm prompt cache makes the second call nearly free, and the rephrased replies were more natural ("Remembered. Asha is your sister's name." vs "Noted."). So `llm.direct_tool_replies = false`; it may pay off on slow hardware or after a CPU fallback.
* **Early clause chunk (built, off).** Speaking a long first sentence from its first comma (`tts.first_clause_chars`) can't help when first speech already starts ~0.25 s after the question, and it costs prosody. Off; a clause chunk does not count toward the sentence cap.
* **Continuous mic (built, off until tried).** `SharedMic` keeps one input stream open for a whole conversation and fans it out: the barge-in monitor while EV speaks and the recorder while it listens each subscribe (immediately, not at first read) and unsubscribe when done, so the device is not closed and reopened between turns and nothing is lost at the hand-off. `conversation.continuous_mic = false` by default because the echo behaviour D20 was tuned on has only been exercised with a fake stream here. **Measured on the real microphone:** two listeners got 20 blocks in 312 ms (real time), a third joined the open stream in 30 ms (one block), nothing left subscribed after close; the first device open took 690 ms (a later re-open was not timed, so no per-turn saving is claimed). **Not verified:** barge-in and the echo tail with a real voice over speakers with this on; try it, and if EV starts hearing itself, raise `conversation.turn_gap_ms` or turn it off.
* **Considered, not built.** Speaking while EV is still thinking (the echo detector stays disarmed until EV has talked for 1.2 s, so speech before the first word of the reply is not caught; handling it means cancelling and merging the turn), speculative transcription at the first pause (a mid-sentence pause would make the final decode wait behind a stale one), and per-query tool subsets (sending fewer schemas would break the prompt-cache prefix this decision depends on and risks missing the right tool).
* **Safety is unchanged.** Parallel batches, direct replies, fillers and smalltalk all sit behind or beside `SafetyGate`; nothing here reads text to decide a permission. Security suite after the change: 88/88, 0 bypasses.

## D22. Phase 1: opening the file EV just made, a tighter "open ..." fast path, user facts out of the persona
What was built, why, and what was and was not measured:
* **The "open" fast path no longer swallows references.** "Open the particular screenshot you just took" became `open_app("particular screenshot you just took")` and answered "I couldn't find an app" without reaching the model. The generic pattern now rejects any name containing a pointing word (it, that, this, last, latest, recent, previous, particular, you, "one I/we/that/from") or a file-like noun (screenshot, file, pdf, image, picture, document). "file explorer" and "one note" are exempt. Trade-off: "open this pc" and "open last pass" now go to the model instead of the app lookup.
* **`open_file` (new tool, `safe`).** "Open it", "open the screenshot (you just took)", "show me the last note" are a deterministic fast-path match to `open_file(which="last")`. `take_screenshot` and `take_note` write `kv.last_artifact` / `last_artifact_kind` (only EV's own code writes them). `take_note` also appends to `data/notes/<date>.md` so a note exists as a file; SQLite is still the record and a failed file write never fails the note.
* **Policy for opening files** (`policy.toml [files]`): only `open_dirs` and only `open_extensions`; no executables, scripts, shortcuts or HTML (opening a file can run it). Because `which="last"` has no path in its arguments, the tool re-checks the file it resolved against the same rule (the D7 pattern). `{screenshots}`, `{skills}` (and, in Phase 2, `{vault_ev}`) are placeholders filled from `ev.toml` by `Config.places()` when the policy is loaded; an unfillable placeholder drops that folder. Decisions still depend only on config and arguments.
* **User facts left the persona.** What `persona.md` said about Sam now lives in `config/seed_facts.toml` and is seeded into memory once (`migrations.seed_from_persona`): an existing fact is never overwritten, a placeholder (`[FILL IN]`) is skipped, and a fact the user later forgets is not re-seeded (the flag is per install, not per key). The persona keeps the rules about how to use facts. `memory.max_facts_in_prompt` 12 → 16 so the seeded facts don't crowd out new ones.
* **Measured** (this machine, `qwen2.5:3b`): 434 tests pass, 1 skipped (373 before; the skip is the symlink test, which needs a privilege this account lacks, so symlink handling for `open_file` is covered only by the shared `path_in_dirs` code and the existing `deny_symlinks` tests, not exercised here). Security suite 88/88 without the model and 96/96 with it, 0 bypasses. Persona eval 30/30 deterministic, judge mean 4.53 (D17 recorded 4.69; D18 notes the run-to-run spread on a 3B model, and I did not take a same-day baseline). Intent eval 64/72 (D18 recorded 62/72); **not a same-day baseline either, so no gain is claimed**; the 8 misses are the same kinds as before (for example "my dog's name is Biscuit, remember that" and "type hello world" return no tool call). System prompt about 1717 tokens against about 1721 before (characters / 3.5 estimate, persona 5873 → 5179 chars plus the facts block), so the context budget is unchanged.
* **Not measured:** the real `os.startfile` call (monkeypatched in tests, so opening a real file from a spoken "open it" has not been tried); voice end to end; anything about the cache effect of the changed prompt beyond the size estimate (the prompt is still byte-stable between turns).
* **Correction, found during Phase 2 (D23):** the persona rewrite in this phase had a cost the persona eval cannot see. With the user facts gone from `persona.md`, the 3B model stopped calling `remember_fact` for "remember that my dog's name is Biscuit" on its own (committed persona 6 of 6, this persona 0 of 6, same prompt). I only ran the memory eval, which would have shown it, in Phase 2. The fast path covers that phrasing in the running app (D23), so what users hit is unchanged, but the model-only path is weaker; see D23 for the numbers and what was tried.

## D23. Phase 2: memory in a Markdown vault with a search index, and memory writes that have to prove where they came from
**What was built**
* **The vault** (`ev/memory/vault.py`): `Facts.md`, `People/<name>.md`, `Projects/<name>.md`, `Daily/<date>.md` in `<vault>/EV` (`[vault] path`, default `~/Documents/EV-Vault`, created on first start-up). EV writes only there; the rest of the vault is read-only to it. Paths are confined by `realpath` (so `..`, symlinks and junctions out of the folder are refused; tested with a real junction) and `[files] write_dirs` in `policy.toml` is a second lock. Obsidian doesn't have to run; plain `[[links]]` and front matter keep it a normal vault.
* **The index** (`ev/memory/vault_index.py`): a separate rebuildable SQLite database (FTS5, `porter unicode61`, bm25), chunked by heading and size, kept fresh by a polling thread (`poll_s`, no `watchdog` dependency), `python -m ev.memory.vault_index --rebuild`. Query text is reduced to quoted plain words, so it can't carry FTS operators. `when` understands today, yesterday, this/last week, this/last month, "last N days", month names and ISO dates. Hidden folders, notes over `max_note_kb`, and links or junctions out of the vault are skipped. Front matter is parsed with `yaml.safe_load` only when it is small and has no anchors, aliases or tags (a note anyone can edit must not be able to expand a billion-laughs document; tested).
* **`recall(query, when)`** returns snippets with file and date, `untrusted=True` (so wrapped as data). Fast-path phrasings ("what did I say about X last week", "what do my notes say about X", "what's in my notes about X", "look up X in my notes", "what did we talk about yesterday") run it and let the model phrase the answer. These patterns are matched **before** web search on purpose: "look up the invoice in my notes" had been going to DuckDuckGo.
* **Facts live in the vault** (`remember_fact` with optional `about`, `forget_fact`, the SQLite table migrated in once through `Vault.add_fact`; if the vault can't be opened EV falls back to the SQLite table). "Remember that...", "..., remember that", "..., keep that in mind", "don't forget ..." are fast-path matches on the transcript, keeping the user's capitalisation.
* **Daily summaries**: `update_summary()` also appends a line to `Daily/<date>.md` (off with `vault.daily_summaries` or `general.log_conversations = false`).

**The two security decisions**
* **Provenance, as escalation only.** `Policy.evaluate` is still config plus arguments and nothing else. The question "is this the user's own words?" depends on the turn, so `Brain` computes it from what the system observed (`ev/safety/provenance.py`: fast path or not; any untrusted tool result or recalled note this turn; how many of the value's content words appear in the user's last three transcripts, threshold 0.8) and passes a reason to `SafetyGate.check(..., escalate=reason)`. The gate can only turn ALLOW into a spoken CONFIRM; BLOCK, CONFIRM and the kill switch are unchanged, and with no asker it fails closed. This is the one deliberate extension of "policy depends only on config and arguments". Overlap is measured against transcripts only and history never holds tool results, so a poisoned paraphrase can't qualify. It measures words, not meaning.
* **The file's labels are never trusted.** `(source: user said)` can be typed by anything that can write to the vault. Each fact line EV writes is recorded in `fact_records` (SQLite, in `data/`) with the SHA-256 of the exact line; `profile_facts()` returns only lines whose hash matches. Hand edits, pasted or forged lines are "unconfirmed facts" (ordinary notes; `recall` can find them, wrapped). "Review my unconfirmed facts" goes through them one by one as `keep_fact` calls (policy `confirm`, `llm_visible = False`), each a spoken readback and a real yes. A plain SHA-256 is enough because the records sit in a database the vault tools can't reach; an HMAC would add nothing against an attacker who can write `data/ev.sqlite`.

**Measured** (this machine, `qwen2.5:3b`, real Ollama unless noted)

## D24. After the first real run: stop the model pretending to remember, and put real facts about the user in memory
**What the first real run (2026-11-02, `logs/ev.log`) showed.** The vault and the seed migration worked on the real machine. Asked "Do you remember? My dog Bistic?" the 3B model answered "Oh, Bistic! He's a loyal furry friend, right?", **inventing** a pet it had no record of (nothing was saved: no tool call, no fact, the rolling summary is clean). Asked "Yeah, so what is in my notes about Lisbon?" the leading "Yeah, so" defeated the fast path and the model made up what the notes might contain. The user had also edited the `work` line in `Facts.md` by hand, and the design handled it correctly: the edited line stopped being trusted (an "unconfirmed fact") until it is confirmed by voice.
* **Fast path.** A few leading fillers ("yeah", "so", "okay", "well", "um", "and"...) no longer stop a match (`_PRE`). "Do you remember ...?" and "you remember ..., right?" now run `recall` (a search of the notes and facts); an empty search tells the model to say it doesn't remember and not to guess; the tool hint says never to add anything the notes don't say.
* **Tried and not kept:** a persona rule "only say you remember something you have a record of". Measured on the model-only path (32 trials each, crude heuristic for "played along"): 16/32 with and without it. Persona wording does not fix this on a 3B model, so the fix is in code, and the persona is unchanged. What is **not** fixed: any other phrasing that reaches the model ("how is my dog doing?") can still get an agreeable invention, about half the time in this probe.
* **Facts about the user** (`config/seed_facts.toml`) were rebuilt from the user's own messages: 232 messages typed across 18 local Claude Code projects, 2026-09-24 to 2026-11-02 (the Claude.ai website chats are not on this machine and were not read). Added: the sign-off name, being a college student who takes part in hackathons, the hackathon results the user listed for their portfolio, their project names, tools (conda only, never venv; Kaggle, Colab, Android Studio, GitHub Pages), how they like explanations (plain, short paragraphs, exact commands), what they want from Evie, and that the assistant is "EV / Evie", never "Eevee". Left out on purpose: anything only implied, contact details, other people, ideas the user floated but didn't build, and anything that reads like a credential. A test fails if the file mentions a pet, a relationship, a birthday, a phone number or a password.
* **Delivery.** `apply_seed_updates` adds keys that are new to the seed file the next time EV starts: it never overwrites an existing fact, and never brings back one the user forgot (every key ever seeded is remembered in kv; installs from before that record are assumed to have seeded the first-release keys). It only applies to an install that was seeded to begin with. It was dry-run on copies of the real database and vault, then applied to the real ones while EV wasn't running: 8 facts added, none changed; the hand-edited `work` line stays waiting for a spoken yes.

The real prompt is now 3155 tokens (it was 2908 before the new facts), leaving room for history.

## D25. Phase 3: a "what's going on" block beside the request
**What it is.** `ev/context/snapshot.py` builds a few lines from cheap local signals and appends them to the **latest user message** on the model path (never the system prompt, so D21's byte-identical prefix and Ollama's prompt cache are untouched; history keeps only what the user said). Signals, each switchable in `[context]`: the foreground app and window title; the next calendar event; up to three files from Downloads, Desktop and the screenshot folder in the last two hours; battery; and the branch and changed-file count of a repo open in the foreground editor or terminal (`context.repos`). The app line is always there; the other lines only when the request is about them (keyword match), and the block is capped at 450 characters.
* **Privacy and trust.** A window of a password manager, a bank, the registry editor or anything the policy's sensitive-window patterns match shows the app name and never its title. EV's own windows are skipped. Titles, file names, event titles and branch names are text other people control, so the block is wrapped as untrusted data (and instruction-like text is flagged), and a turn that included any of it counts as having seen untrusted text: a fact the model tries to save that turn needs a spoken yes (D23). The fast path never builds the block.
* **Calendar** (`context/calendar.py`): `calendar_source = "none"` is the default, so no calendar is read until you set `"ics"` (a file; single events only, recurring events are not expanded) or `"outlook"` (classic Outlook through COM, read-only). A background thread refreshes it every 5 minutes and the snapshot only reads the cache, so a slow Outlook can't delay a reply. `get_agenda(day)` exists only when a calendar is configured (so it costs no prompt tokens otherwise) and returns untrusted text.
* **Measured** (this machine): building the block takes **0.52 ms median, 1.08 ms p95** over 50 runs with the folder listing uncached (`python -m ev.evals.bench context`; foreground 0.08 ms, battery 0.01 ms; a 300-file folder listing 0.8 ms in a separate profile; the files and git signals found nothing to report at that moment, so they were timed separately, not in that run). The profile found one real cost I had introduced: `windows.own_pids()` walks every process and takes **82 ms**; it is now computed once when the snapshot is created. Against real Ollama with the warm prompt and tool list, a 400-character block in the user message took a median 477 ms per request against 407 ms without it, while Ollama's own prompt-evaluation time was 17 ms in both, so the prefix is not re-evaluated; I did not isolate what the extra 70 ms is (reply lengths differ between runs).
* **Not measured:** the Outlook reader (Outlook is not installed here; tested with fakes only), whether the block improves or confuses the 3B model's answers (no eval for it), the git signal against a real editor window, and behaviour with several monitors or full-screen apps.

## D26. Phase 4: skills (routines made of ordinary tool calls)
**What it is.** A skill is a small TOML file in `skills/` (name, trigger phrases with optional `{parameters}`, ordered steps that are ordinary tool calls, optional closing line, optional short Markdown instructions). Three ship: `work mode` (open VS Code, search YouTube for `{music}`, default "lofi beats"), `morning brief` (time, weather, calendar, reminders; a few lines of instructions for the model) and `wind down` (stop media, volume 30, half-hour timer). They run three ways: the fast path when the whole sentence is a trigger phrase (no model, e.g. "work mode with jazz"), the model's `run_skill(name, options)` tool (name is an enum built from the files), and later the dashboard.
* **Every step is gated on its own.** A step is run by the same code as a spoken request (`Brain._execute`: argument validation, `SafetyGate`, provenance), so a skill can never do more than the user could ask for, a risky step asks out loud, and a refused step stops the skill and says which one ("Stopped at step 2, open app: not allowed..."). A step marked `optional` is skipped if its tool is unavailable or fails for an ordinary reason (the weather with no home city), but a step the gate *refuses* always stops the skill. The audit list gets one entry per step plus the `run_skill` call.
* **What a skill cannot contain.** `run_skill`, `save_skill`, `manage_skill`, `keep_fact`, `build_task`, `remember_fact` and `forget_fact`; more than 10 steps; arguments that aren't plain values; a `{parameter}` that isn't declared; a file over 20 KB; instructions over 120 words. A file that fails any check is reported in the log and skipped, never run half-checked. Parameter values are cut to 100 characters with braces removed and substituted in one pass, so a value cannot carry a template of its own.
* **Teach by doing, by voice only.** "Save that as focus time" turns the successful calls from the last 15 minutes (at most 6, memory and skill tools left out, repeats collapsed) into a skill file, reads the steps back and invites another trigger phrase ("also run it when I say pad"). Renaming, listing and deleting are by voice too; **deleting is a spoken yes** (policy escalates `manage_skill action=delete`). `save_skill` and `manage_skill` are not in the model's tool list (a skill is a standing automation, so the model cannot create or change one; tested). Files are written only inside `skills/` (policy `write_dirs` `{skills}` is a second lock). A skill file is not set as `last_artifact`: `.toml` isn't an openable type (D22).
* **The model reaching for a skill on small talk.** Measured with the real model and stub tools: "tell me a joke" made `qwen2.5:3b` call `run_skill` in 5 of 6 trials (then 6 of 6), which would have run `wind down` (stopping media, setting the volume). So a model-made `run_skill` is judged like a memory write: refused outright if nothing the user said shares a word with the skill's name or trigger phrases; asked about if only some of it does or if untrusted text was read this turn; silent otherwise. After the change, small talk executed 0 of 6 skills with no question asked; the three loosely worded real requests ("let's start my work mode with some jazz", "I want to wind down for the night", "get me ready to work, put on some rock") still picked the right skill 6 of 6 each and ran without a question. "Brief me on my day" is not a trigger and the model chose another tool 6 of 6; the exact phrases ("morning brief", "brief me", "start my day") work.
* **Instructions only while the skill runs.** The morning-brief guidance is in the tool result of that turn (beside the wrapped data), not the system prompt; a test checks it is absent from the system prompt. Tool results with a `hint` now pass it to the model whether or not the result is untrusted.
* **Measured:** 722 tests pass, 1 skipped. Security suite 137/137 with the model, 129/129 without it (88 and 96 before Phase 2), 0 bypasses. Persona 29/30 (one all-caps reply; the usual spread), memory 7/8 (`llm_forgets_on_request`, as on the committed code), intent 66/72. **Mutation check:** if a skill step bypasses the gate, 7 skill cases fail (the `cmd.exe` step runs; a force-close happens with nobody asked), and none fail with it in place. Real prompt: 3155 → 3261 tokens (+106, of `num_ctx` 6144) for `run_skill` and `list_reminders` (`save_skill` and `manage_skill` are hidden from the model).
* **Not measured:** a real spoken session of saving a skill, the shipped skills against real apps (every test uses stub tools: opening Visual Studio Code and YouTube was not tried), the morning brief's wording from the model, a skill with a confirmation step in a real conversation, and the cost of a long skill (steps run one after another; no timing was taken).
* **Known limits:** `{music}` and other parameters come from the trigger phrase only; a skill can't branch or loop; a saved skill replays the arguments exactly as they worked (a one-time URL, say) and the policy judges them again each run.

## D27. Phase 5: EV speaking up on its own (proactive rules), as timid as possible
**What it is.** `config/proactive.toml` holds rules: a source (what to watch), settings, and what to do: say a line, show a short card, and/or run a skill. Sources: `time` (a time on chosen days, once a day, within a window), `calendar` (N minutes before the next event; needs a configured calendar), `process_exit` (a build tool such as cargo or msbuild that ran at least N seconds has finished), `file` (a file matching a glob appeared and stopped growing), `battery` (below a level, not charging; re-arms when plugged in or 5 points higher), `app_time` (N minutes in one app), and `event` (another part of EV announces a topic, for the Claude Code jobs of Phase 6). Starter rules: low battery, long build finished, morning brief (09:00 on weekdays within an hour, only if the user touched the keyboard in the last 10 minutes), and meeting soon (**shipped off** until a calendar is set).
* **Lines are system text.** A spoken line or card is the rule's own template filled with a few fields from the source (a process name, an event title, a file name), cleaned (tags removed, 60 characters, whitespace collapsed). A template may only use the fields its source provides, checked when the file is read. No model writes the line, like the "one sec" fillers (D21). The one exception is a skill that fetched outside text: then `Brain.phrase_for_speech` makes one model call with **no tools**, the data wrapped as untrusted, at most three sentences, any that names a tool dropped; if the model is down, nothing is said.
* **The guards** (all in `[guards]`): quiet hours (22:30 to 07:30, wrapping midnight); a full-screen app, game or presentation (`SHQueryUserNotificationState`); a call (another program using the microphone per the Windows consent store, with EV's own `python.exe` excluded, or a call app in front); not while a turn, follow-up window, confirmation, mute or pause is on; nobody at the keyboard for 30 minutes; at most 4 spoken lines an hour; and a snooze ("quiet for an hour", "you can talk again"; remembered across restarts, `snooze_proactive` is voice-only and cannot be called by the model). A line a guard holds back is retried and **dropped after 10 minutes**, never delivered stale. Cards are silent, so quiet hours and calls don't hold them, but a full-screen app does.
* **A skill started by a rule never asks.** `SafetyGate.check` got an `ask_allowed` option (escalation-style: it can only make an answer stricter). Every step of a proactive skill is validated, gated and judged as usual, but a step that would need a spoken yes is refused ("Stopped at step 2, close app: not allowed: that needs your approval, and I don't ask for it on my own"), because EV does not start a question on its own. Mutation check: letting it ask makes two security cases fail (a prepared "yes" lets it force-close Chrome and open an administrator app); with it in place, none fail.
* **Overlay.** A new `notice` message (validated like the others) shows a short card for a few seconds even with display mode off; a real conversation line takes the card over, and a notice never changes display mode.
* **Measured** (this machine): the real probes work and are cheap (idle time 0.02 ms, notification state 0.07 ms, microphone-in-use registry check 0.3 ms, battery ~0 ms, a 15-file glob 2 ms, a process scan about 12 to 14 ms). The first process scan took **2.9 to 3.2 s** (cold), so the slow sources run on the engine's own thread, outside its lock, so a snooze or an event never waits on them. A normal tick takes 0.01 ms; with the shipped rules and the real probes the engine is about 0.14% of one core. 799 tests pass, 68 of them new; security suite 137/137 without the model (8 new proactive cases), 0 bypasses.
* **Not measured:** a real morning brief at 09:00 on a weekday, the call and full-screen guards against a real Zoom call or a real game (the registry check was only run with nothing using the microphone), the file source against a real download, the app-time rule over a real afternoon, and the card on screen (tested through the Qt model offscreen). The `process_exit` source can only see programs whose image name is the tool (cargo, msbuild...), not a `pytest` run inside `python.exe`.
* **Known limits:** snooze understands durations ("an hour", "30 minutes"), not "until five"; the calendar rule is as limited as the calendar reader (D25); a held line that is dropped is only visible in the log and the engine's recent-events list, not announced.


## D28. Phase 7: a local dashboard that can watch and tune EV but cannot widen it
**What it is.** A small web page on `127.0.0.1` (stdlib `ThreadingHTTPServer`, Server-Sent Events, one vanilla HTML/JS/CSS page, no new dependency), opened by saying "open the dashboard" or from the tray (`[dashboard]` in `ev.toml`; `enabled = false` means no listener at all). Tabs: Live (state, the current exchange, each tool call with the gate's decision and timing, timers and reminders, what the proactive engine did, snooze), Settings, Voice and model, Skills, Memory, Policy (read-only). Pause, Mute and Stop-everything are the same actions as the tray's; they only reduce what EV does.
* **Signing in.** Each visit starts from a one-time link EV opens for you (`/?t=<token>`, valid once and for two minutes). The server trades it for an `HttpOnly; SameSite=Strict` cookie and redirects, so the token never stays in the address bar or history. Every request then needs that cookie and an exact `Host` (stops DNS rebinding); a POST also needs an exact `Origin`, `application/json` and a body under 64 KB. Responses carry a strict `Content-Security-Policy` (no inline script or style, nothing external) and `no-store`; the page puts every piece of text into the DOM as text, never as markup (a test greps the script for `innerHTML` and friends).
* **Settings are an allow-list, not a filter.** `ev/dashboard/settings_schema.py` lists 30 tuning keys, each with a type and range (follow-up windows, reply length, temperature, pauses, the text card, what the context block shows, how often proactive lines may come and quiet hours). A key that isn't listed returns 403 and the whole request is refused. They are written to `config/ev.local.toml` only (atomic; the first write keeps a `.bak`; comments in that file are not kept). Everything that could widen access stays file-only: `builder.*`, the vault and every other path, web hosts, `context.repos`, the calendar, privacy, hotkeys, the model server address, the proactive rules, and **every value in `policy.toml`**, which is shown read-only; there is no route that writes it. `tests/test_dashboard.py` walks `ev.toml` and `policy.toml` and fails if an allowed key is in a non-tuning section, has a widening word in its name, or is a policy value; the guard is itself tested with keys it must catch.
* **Live or restart.** Each setting says which. Live: reply length, temperature, filler delay, sentence pause, display mode, the context switches, the proactive guard values (`apply_overrides` in `proactive/rules.py` also reads them at start-up, with the same range checks as the rules file), and the conversation timings (read each turn). The wake-word threshold and the card's size and linger need a restart, and the page says so.
* **Everything that acts goes through the gate.** Running a skill is `Brain.run_skill_for_user`: the same `_execute` per step as a spoken run, so a risky step still asks out loud and a refused step stops it. Deleting a skill is a spoken yes. Forgetting a fact is `forget_fact` from the "dashboard" source, which provenance treats as not-the-user's-words, so EV asks out loud. Confirming an unconfirmed fact is `keep_fact`, which asks for a spoken yes: a click can start the question but never answers it. Saving a skill is validated like a file (forbidden tools, step count, undeclared parameters, a tool that exists) and cannot choose its own instructions file. An action that could talk or listen takes `_turn_lock` and answers 409 if a conversation is going on.
* **Voice and model.** Voices come from the files that are installed (Piper voices with a `.json` beside the `.onnx`; Kokoro English voices from `voices-v1.0.bin`, read with `allow_pickle=False`), and the requested name must be on that list. `Speaker.swap_engine` loads the new voice and makes it say a short phrase first; on any failure the old voice keeps speaking and the page says why. "Try it" switches until restart, "Use and save" also writes `ev.local.toml`. Chat models come from Ollama's `/api/tags` with a warning above `llm.vram_budget_gb` (3.2) and a background prompt-cache refresh after a switch.
* **Measured.** 861 tests pass, 1 skipped (61 new, in `tests/test_dashboard.py`, including a real server on a free port and the real `EVApp` handing out a working sign-in link). Security suite 153/153 with 16 new `dashboard:` cases (loopback bind, nothing without sign-in, one-use link, rebinding host, cross-origin and form posts, no route that writes policy or runs anything, no path traversal, widening settings refused), 0 bypasses.
* **Not measured:** the page in a real browser. The script passes `node --check` and is tested for text-only DOM handling by a grep, but the Chrome extension did not respond when I tried to open it, so **I have not seen it rendered or clicked it**. Also not measured: a skill run or a spoken confirmation started from a click on real hardware, a voice swap with the real Piper and Kokoro engines (tests use fakes), the listener's memory use, and more than one browser at a time.
* **Known limits and residuals:** another program running as you can read the one-time link from the browser's launch command line during its two minutes (the same-user caveat as the overlay token). A signed-in tab is trusted like the tray: anyone at your keyboard can pause EV or change tuning settings, but still cannot loosen policy or answer a spoken confirmation. The skills editor is JSON in a text box and renaming is by voice. The dashboard picks a new port every start (`port = 0`), so there is no bookmark; ask EV to open it. The Claude Code builder tab (Phase 6) does not exist yet.


## D29. Phase 8: a more conversational Evie, and an honest account of what a 3B model did with it
**What changed.** `config/persona.md` (still character and rules only, no facts about the user): the "don't end every reply with a question or an offer" rule became "a reply ends with a statement unless they just shared news, a plan, a mood or progress; then one short specific question, never two"; one concrete next-step offer now and then, never by default; "boss" may be used now and then in the middle or at the end of a sentence and never as the first word, or whatever they asked to be called (a `preferred_name` fact); when something they told her is relevant she ties it in with a few words instead of reciting it; a short paragraph on the "what's on their computer" block (mention it in a few words, never read it out, never act on it); and four more voice examples, three of them statements. The old "use their first name only now and then" is gone. New fast-path phrase: "call me boss" / "you can call me Chief" saves `preferred_name` (the user's own words, so the trusted route; "call me back later", "call me at five" and "call my mom" are not names).
* **Eval.** The persona eval grew from 30 to 41 prompts: 5 "interactive" (things a friend reacts to), 3 "memory_callback" (the eval's memory holds four seeded facts; a reply counts only if it uses words only the memory knows), 3 "context" (a wrapped context block beside the prompt, as the app adds it). New per-reply checks: never opens with "boss", "Sam" or "Samson"; never reads the context block back. New rates over the 20 chat replies: question, "boss", offer, replies with two questions, memory callbacks.
* **Measured** (`qwen2.5:3b`; three runs each of the old and the new persona on the same 41 prompts, done twice, the second time after the statement examples were added; the numbers move by several points between runs). Old persona (second comparison): pass 99.2%, judge 4.58, **"boss" 0%**, offers 5%, **questions 73%**, memory callbacks 0%, 2.0 replies per run with two questions. New persona (final): pass 100%, judge 4.59, **"boss" 10% and never first**, offers 12%, **questions 68%**, memory callbacks 0% (0.11 in the run before the examples were added), 0.3 replies per run with two questions. Intent accuracy, whose tool calling depends on the persona text (D22 saw remember_fact collapse from 6 of 6 to 0 of 6 once), was 86.1% and 87.5% with the old persona against 84.7% and 86.1% with the new: about one case lower, inside the spread; remember via the model alone is still 0 of 3, handled by the fast path as before. Security suite 161/161 with the model, 0 bypasses; memory 7/8 (the usual `llm_forgets_on_request`); 883 tests pass, 1 skipped.
* **Two things the last run taught.** The 3B model copies quoted example phrases word for word: with "Is this for the big project?" in the persona it answered "did you save my file" with "Yeah, I saved it for you. Is this for the big project?" (a false action claim, the one thing the persona eval must never pass), so the callback examples were removed and the instruction now has none. And the "never first word" rule failed once ("Boss, I'm not sure..."), so it is also enforced in code: `drop_name_opener` removes a vocative "Boss," / "Sam:" from the first sentence of a model reply (not from a name later in the sentence, not from "Boss battles...", never emptying a reply). With both changes the persona eval passed 41 of 41 three times in a row (question rate 60, 70 and 65%; "boss" 10, 15, 15%; offers 5, 10, 15%; callbacks 0%; judge 4.50 to 4.56).
* **What did not work, plainly.** The goal was a follow-up question in about one reply in three. The 3B model asks one in roughly seven of ten replies with either persona, whatever the wording: more positive wording ("one in three") raised it to 85% in one run, a negative-first rule and statement-heavy examples brought it back to where it started, and nothing took it near 33%. Memory callbacks barely happen either: given "I have a hackathon next month" with the wins in its prompt, it says "That's awesome, boss!" and not more. These behaviours need a bigger model or fine-tuning (the Phase 9 notes), not more prompt text. I did not add a code filter that deletes trailing questions, because it would also delete the ones that matter ("Which one, Chrome or Edge?").
* **Cost.** The persona is 330 tokens longer (6.6 KB, from 5.3); with the tool list the real prompt is about 3,600 of the 6,144-token window, and `test_real_prompt_leaves_room_for_history` passes.
* **Not measured:** a real conversation of any length (the eval is one prompt at a time, with history cleared), whether "boss" feels natural or grating in speech, the nickname rule (no eval uses `preferred_name`), and the context-block paragraph against the real block built by `ContextSnapshot` (the eval uses a short stand-in).


## D30. Phase 9: groundwork only (fine-tuning export, a QLoRA outline, two design notes)
**What exists.** Nothing here changes how EV runs.
* `scripts/finetune/export_data.py`: turns an opt-in `data/training/turns.jsonl` and the 72 intent-eval utterances into chat-format `train.jsonl` / `val.jsonl`. It is a dry run unless `--yes` is given; it redacts (`ev.core.log.redact`, plus emails, phone numbers, URLs, Windows user folders, long digit runs); it **drops every turn in which web, screen, file or note text reached the model** (`untrusted: true`), turns with a failed tool call, and rows marked `keep: false`; a tool turn trains on the call, not on what the tool returned. `tests/test_finetune_export.py` (4 tests) covers the redaction, the drops and the opt-in.
* `scripts/finetune/qlora_qwen25_3b.ipynb`: an outline for Colab or Kaggle (the laptop's 4 GB cannot train a 3B model): data check, QLoRA config, train, GGUF export, `ollama create`, and a gate that replaces the base model only if it is no worse on intent, persona and memory and has **0 security bypasses**. No cell has been run.
* `docs/design/SPEAKER_VERIFICATION.md`: the planned mitigation for the fast-path "remember that" residual risk (D23) and for other voices in the room. Escalation-only, thresholds from measured error rates, voiceprint stored as a vector never as audio, enrolment by voice only; says plainly that a replay of the owner's voice passes, and lists two cheaper fallbacks.
* `docs/design/PHONE_ACCESS.md`: a hub on the Tailscale or LAN interface only (never `0.0.0.0`, never the internet), a PWA with push-to-talk, QR pairing confirmed by a spoken yes, per-device keys and four tiers (watch, chat, act, act-and-confirm with a number-match), the threat-model rows to add when it is built, and what is deliberately left out (calls, push notices).
**Deliberately not built.** EV does not record conversations for training. That is a decision about storing the owner's speech and text (even locally and redacted), and the one real dataset, 72 utterances, is too small to train on, so collection is left for the owner to turn on, with its own opt-in switch, once they want it. Fine-tuning is the realistic fix for the two things prompts could not change in D29 (the question habit, memory callbacks), which is why the outline exists.
**Not measured:** everything. The export script was run only on its own tests and a dry run over the eval seeds; the notebook, the embedding models, Tailscale on this laptop and the PWA microphone path have not been tried.
